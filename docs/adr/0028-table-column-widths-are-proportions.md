# Table column widths are stored in pixels and shown as proportions

The Admin drags table column widths in the editor with Tiptap's built-in column resizing, and they are stored the way Tiptap stores them: a pixel `colwidth` per cell, one entry per column the cell spans. The public page does not use those numbers as pixels. Pixel widths dragged in the roughly 975px editor clipped published tables in the narrower public article and on phones, which is why f7ca4003 turned resizing off and ignored stored widths. Instead each column gets its share of the stored total as a percentage, in a full-width `table-layout: fixed` table, so a table keeps its proportions at any viewport width. A column without a stored width counts as the average of the stored ones, and a table with no stored widths still sizes its columns by content. On narrow screens the table keeps the narrowest column at least 5rem wide, but never asks for more than two thirds of its stored pixel total, so a table laid out in the wider editor still fits the published article on desktop, and below that it scrolls sideways in `fuwari-table-scroll` rather than clipping. The editor and the read-only Post Revision view show the same proportions through one shared calculation, so a table is full width in both places. Because the table always fills the content column, dragging a border trades width with the column to its right instead of growing the table. Posts published before this change that still carry stored widths now show them.
